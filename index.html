Ninth Tool

Ninth Tool executes your page's WebMCP tools in the browser and shows which promises the standard silently drops, with the command that reproduces each one.

Named for the tool that has to disappear. A conditional tool appears when the state that justifies it appears, and it is supposed to withdraw when that state goes away. Write the withdrawal the obvious way, with the abort signal on the descriptor rather than in the options bag, and it never happens, and nothing is thrown.

Run it

This drives the subject page below through your browser's own WebMCP and judges what happened. Nothing is sent anywhere and nothing is stored. On any page but this one it calls only tools marked read only; here, where the subject page is ours, some rows drive its forms as well.

The behaviours

This page is a WebMCP page too

Both halves of the standard on one surface. This page publishes tools of its own, so your agent can run the whole audit without touching the screen, and the subject page it drives publishes two more from nothing but HTML attributes.

read only

nt_list_behaviours

Every behaviour this suite tests, filterable by group.

read only

nt_explain_behaviour

One row in full: the promise, what the specification says, what was measured, and the command that reproduces it.

not read only

nt_run_audit

Runs the audit and returns the counts. Marked not read only, because it drives forms on the subject page below, and saying otherwise would be exactly the dishonest annotation this suite exists to catch.

read only CONDITIONAL

nt_get_findings

Reads the findings from the run. It does not exist until an audit has produced some, and it is withdrawn when they are cleared. Registered with the abort signal in the options bag, which is the only place that works: behaviour C2 exists because putting it on the descriptor fails silently. Run the audit and the tool count moves from three to four, then press Escape and watch it go back. It is the fourth tool this page registers, not the ninth: the product is named after the behaviour, not after a position in this list.

Every one of them validates its own arguments, because behaviour C3 measured that the browser validates none, and every one refuses by returning a result rather than throwing, because behaviour B1 measured that throwing erases the message.

The subject page

A real page on this origin with two forms promoted to tools by HTML attributes. It is loaded in a frame and driven live. You can fill either form in yourself: they are ordinary controls when no agent is involved.

What this does not do, and why

It does not scan other people's sites. A page cannot reach another origin's tool surface. The tools Permissions Policy defaults to self, and a cross origin frame was measured contributing zero tools while a same origin frame contributed its whole list. That boundary is the reason this is a suite you run against your own page rather than a scanner you point at a stranger's.

To audit a page on another origin, run the command line runner against it from a machine you control:

node bin/ninthtool.mjs https://your-page.example

The probe calls only tools your page marks readOnlyHint. A tool carrying no annotations is never called, and that refusal is reported as a finding, because a page that gives an auditor no way to know a tool is safe gives an agent no way either. Two rows submit a form, which is a write, and they run only against the subject page this suite ships. No account, no backend, no crawling, and no verdict is published about anybody's named page.

This page fails two of its own rows

P1 fails because two of the tools on this surface come from HTML forms, and the standard has no way to annotate a form derived tool at all. That is behaviour B4 above. It is not something this page can fix, and pretending otherwise by hiding the row would be the dishonesty this whole suite exists to catch.

P4 fails because this page and its subject frame share one origin, so they share one tool surface. Whichever of the two documents you measure from, the other one's tools are sitting on it, and nothing on the surface says where they came from. That is the finding, not an accident, and it is worth seeing on a page that admits it before you meet it on one that does not.

P5 failed here too, on the first run that measured it, and that one was a real defect. The tools on this page did not check their own arguments, in a standard where the browser checks nothing on the script path. They do now, and the row is green. The suite found it in its own author's code, which is the most useful thing it has done so far.

Where the numbers come from

Every stored measurement in the catalogue was taken on 2026-09-01 against Chrome 152.0.7977.65 launched with --enable-features=WebMCP. Nothing in it is copied from documentation. Where documentation disagrees with the measurement, the row says what the documentation promised and is reported as a divergence rather than as a defect in your page.

The reading above is not that stored measurement. It is what your browser did, just now, and it may differ. Where it does, your browser is the newer fact.
